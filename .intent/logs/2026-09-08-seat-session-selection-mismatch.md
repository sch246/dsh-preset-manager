# New-session preset display mismatch

The user reported an intermittent mismatch: the new-conversation page already showed 极简模式, but sending the first message started 标准模式. They confirmed that the official selector did not exhibit this symptom and requested a plugin repair.

The plugin retained `manualSelection` across Session navigation after consuming `pendingApply`. Its no-pending branch returned without reading the new Session's actual preset; the official selector reads that preset back. Initial roster selection also changed the label without applying the chosen preset. These mechanisms explain why the mismatch depends on prior selections, default settings and blank-Session reuse.

The repair binds selections and successful responses to a Session identity, applies initial choices through the existing selection endpoint, and reports the committed preset while a replacement is pending. Repeated notifications share one request; responses belonging to an earlier page cannot update the current page. A Remote confirmation is temporary until the list projection catches up. Failures retain a visible error and allow a manual retry. Preset-group start passes the selected Session identity before synchronous navigation.

Validation used a private Home and the actual installed profile package set with the candidate plugin. Typecheck and build passed. Temporary controller probes exercised Session changes, delayed replies, duplicate notifications, default retention and failure/retry. Real Chromium interactions confirmed manual selection, a subsequent new Session, menu default persistence and page reload; a deliberately held selection request did not overwrite a subsequent Session, and pressing Enter in the real composer started the first turn with the Host projection `minimal`. The final browser-load gate reported 48 entries, one preset-manager entry and zero errors. These observations do not claim an exhaustive audit of every plugin interaction or user acceptance.
